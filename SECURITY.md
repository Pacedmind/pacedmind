# Security

PacedMind starts Claude Code and Codex in terminals on your computers. Anyone who could make it start a session could run code on your computer, so the design assumes the worst about everything outside the computer: the cloud database, the web app, a stolen password, a stolen browser session, and even the agents' own conversations.

Without an account (the free One device plan), the desktop app keeps its data in a SQLite file next to its settings (`src/server/store/local.ts`), and nothing leaves the computer. Everything under "Your computer", "Agents" and "Starting sessions" applies the same way; "Accounts" and "Your data" are about PacedMind Cloud, which the app switches to once you sign in (`src/server/scope.ts`).

## Reporting a vulnerability

Report security problems privately, not in a public issue: select **Report a vulnerability** on this repository's **Security** tab, which opens an advisory only the maintainer can see, or email mbednarczyk@preseed.tech. Say what's affected, how to reproduce it, and what an attacker could do with it, and give us time to release a fix before you tell anyone else.

This covers the desktop app, the MCP server, the web app at app.pacedmind.com, and the database rules and billing functions in `supabase/`. Test only with your own accounts, computers and data: your own PacedMind Cloud account, or a local Supabase stack (`npx supabase start`). Denial of service and spam are out of scope.

## What protects what

### Accounts

- **Two-factor sign-in can be enabled later.** Accounts without a verified factor can use the planner and connect MCP after signing in. Once an account enrolls a factor, every sign-in must verify it. The database checks live verified factors, not user-editable metadata or an old user snapshot. Settings → Security enables the first authenticator; accounts already using MFA keep their protection.
- **The database separates planning from computer access.** `private.planner_session_ok()` accepts only a live human session: `aal2`, or `aal1` when the account has no verified factor. `private.session_ok()` remains strictly two-factor. `private.computer_session_ok()` additionally requires the verified factor to predate this sign-in. Revoked and expired sessions, and OAuth sessions posing as humans, fail these checks. Restrictive RLS policies still combine with ownership rules.
- **Fresh codes for dangerous things.** Starting, resuming or sending back a session from afar and deleting the account need a code entered in the last five minutes, and the database checks it itself (`private.recent_mfa(300)`). The code only counts when it came from an authenticator the account already had before this sign-in: Supabase lets any signed-in session add an authenticator, so a stolen session could otherwise add its own and pass every check. The app skips asking again for a code entered in the last four minutes; the database still decides. The one exception is a computer whose own **Two-factor code** setting is off: requests to it need no code (see "Starting sessions").
- **Changing what protects the account.** The first authenticator can be added from a basic sign-in; another needs an existing code. Removing one needs a code from one that stays. Password changes require the current password and, when MFA is enrolled, its code. Password recovery requires the email-link session and, when enrolled, MFA. Account deletion requires a recent existing-factor code, or, for accounts without MFA, password/recovery authentication within five minutes. A separate short-lived public-key client reauthenticates a password for deletion; it is always signed out afterward. A renewing subscription still prevents deletion.
- **Email links use PKCE only**, so a link made for someone else's account can't sign your app in.
- **Signing in with Google** replaces the password. An account with MFA still enters its code; an unenrolled account can plan and connect MCP. Google returns through PKCE. A Google-only account can use an email confirmation link for account deletion without first adding a password or MFA.
- **Web sessions live in HttpOnly cookies** (no script in a page can read them), and there is no Supabase secret or service-role key anywhere in the app: it talks to Supabase with the public publishable key and your own session, so row level security applies to everything it does. (Only the billing webhook, which runs inside Supabase, uses the service role; see Billing.)

### Your data

- Every row belongs to one account. References between rows include `user_id` (composite foreign keys), so a row can't point at another account's rows even by mistake.
- `anon` has no privileges at all; `authenticated` can't truncate tables or write bookkeeping tables (`user_state`, `key_counters`), and changes devices and launch requests only through narrow column grants and functions. A launch request is decided once (waiting → outcome), and a computer's entry can't be taken over by another session.
- **Computers.** Any two-factor session of the account can rename a computer or make it the default (one per account, only a signed-in one; signing it out clears it). What a computer reports about itself (when it was last seen, what it found of the agents, its PacedMind version, its settings for requests from elsewhere, including whether they need a two-factor code) changes only from that computer's own sign-in, so another browser can't make it look online, change what it shows, or switch its code off. The computer takes over a name given elsewhere; names are plain text.
- Checks on every text column keep values in the shapes the app expects: task keys like `WRK-12`, dates, colors, sizes. Settings in the cloud can only be work hours.
- **Notifications on your phone and in browsers (web push).** A browser that asks for them (Settings → Notifications) saves its push subscription to the account: the push service's address, which the database takes only from Google's, Mozilla's, Apple's and Microsoft's push services, so a subscription can't aim a computer at another address, and the browser's keys. The account's VAPID key pair (`push_keys`) is made by PacedMind the first time a browser asks, and kept in the account like the rest of its data, readable only by its two-factor sessions; it only lets someone send notifications to the account's own browsers. Keys and subscriptions are added and deleted, never changed in place. The computer a session runs on sends the notifications itself (`src/server/push.ts`), encrypted for each browser: the task's key and title, what the agent asks or said (240 characters at most) and a path in PacedMind. The service worker (`public/sw.js`) opens only a path on PacedMind's own site. A subscription the push service says is gone is deleted.

### Billing

- **Stripe is the merchant of record** (Managed Payments, on in the live account): it sells the subscription, charges and pays the VAT, and handles disputes. With it on, Checkout takes no text of ours (`custom_text`).
- **Card details never reach PacedMind.** Subscribing, the card, invoices and cancelling happen on Stripe's own pages (Checkout and the Customer Portal), opened from Settings → Plan. Neither the desktop app nor the web app holds a Stripe key.
- **Three Edge Functions in Supabase talk to Stripe** (`supabase/functions/`), with Stripe's key and the webhook's signing secret in Supabase's secrets. `billing-checkout` and `billing-portal` act for the caller's own session: they read its billing row through row level security, so an incomplete MFA sign-in, a signed-out session or anyone else gets nothing, and they only open pages for that account's own customer. They return the payment page to fixed addresses (the web app's Settings, or pacedmind.com/subscribed for the desktop app), never one the caller names. The price is the country's own, found by its lookup key; switching between monthly and yearly keeps the country the subscription was bought in, and the Customer Portal offers no switching, so nobody moves to another country's price.
- **Only the webhook writes billing** (`stripe-webhook`). It takes only requests Stripe signed, reads each subscription back from Stripe rather than trusting the event's copy (so a replayed or reordered event changes nothing), and writes only the `billing` table, with the service role. Accounts read their own row and change nothing in it.
- **The database decides who may write.** Once billing is on (`private.billing_switch`), a statement trigger on the data tables refuses inserts and updates (SQLSTATE PT402) from an account whose trial and subscription have ended. Reads, deletes and a computer's reports about itself go on, so its data can always be seen, deleted and moved back to a computer; settling what already waits (a request's outcome, an answer) goes on too, but nothing new starts. Changing the app's code can't get around it.
- **An account whose subscription would renew can't be deleted** (`delete_account`), so it isn't charged after it's gone.

### Your computer

- **Floating task notes.** Agents may request a window for an existing task, with a display id and the user's answer about remembering it. A launched session can request only its own task. Cloud requests require established computer access, belong to the account (composite task and device foreign keys), expire after two minutes, and only the destination computer may dispatch or settle them. Claiming before delivery prevents retries from reopening a closed note. Display reports come only from that computer's own sign-in; a remembered choice lives locally, per planner. The Electron bridge accepts only its main-process window-key header and rejects browser origins. It checks the current account and task creation time before dispatch; the note checks both again on reads and writes. Requests carry no executable content, paths or navigation URLs.

- **Area workspaces stay on this computer**, alongside project and task folders in `device.ts`. Only the local window sets them, through `setAreaFolderAction`, with the same path checks as project folders. A session inherits its task's folder, then its project's, then its area's workspace. Data moves copy these local mappings to the new area ids; resets and deletions remove the relevant mappings.

- **Nothing in the cloud decides what runs.** The agent commands, the terminal, each project's folder and the MCP tokens are this computer's own settings (`src/server/device.ts`), changed only from the desktop app's window. The launcher checks the task's key and title from the cloud against strict patterns (or reduces them to letters and digits) before they reach a command line, refuses folders with characters a terminal would act on, and never takes a folder or a command from a database row.
- **What a task needs only picks which computer to offer.** A task's needs (`Task.needs`, `src/lib/needs.ts`) are names the database holds to plain characters, at most ten, matched against the names each computer said its agents have. They decide which computer the Start button and Run on a computer offer, and what an agent's request to start a session warns you about. They never start anything, name a folder or a command, or let a request skip its fresh code; a request from elsewhere isn't checked against them, since whoever sent it picked that computer.
- **Only the app's window can use the app.** The server answers on 127.0.0.1 only, refuses other Host names (DNS rebinding), and refuses every page, Server Action and API call that doesn't carry the window key: the desktop app makes a new key each run and gives it to its window as an HttpOnly cookie. Other programs on the computer, other Windows users, and the agents PacedMind starts can't drive it. Every Server Action checks the key again, and while you're signed in to Cloud the planner sign-in policy too (`guardAction()`). Computer operations independently check `can_control_computers()` in actions, the launcher and MCP tools. Before trusting a server with its window, the app has it sign a random value with that key, so another program listening on the port can't pose as PacedMind.
- **Secrets are encrypted at rest.** The sign-in session and this computer's settings (`session.json`, `device.json` in `%APPDATA%\Organizer\data`) are encrypted with AES-256-GCM, with a key the desktop app keeps in the OS keychain (Windows DPAPI through Electron `safeStorage`). An unencrypted or unreadable file there is set aside, not trusted.
- **A strict Content Security Policy** with a nonce per request, plus `frame-ancestors 'none'`, `nosniff`, `no-referrer` and a restrictive `Permissions-Policy`: task titles and descriptions come from the cloud, and a page running foreign script could otherwise start sessions.
- **A project's repository, not its folder, goes to the account.** So your computers recognize one project in their own copies, the computer with a project's folder saves which git repository it holds (`src/server/git-remote.ts`): the remote's host and path, lowercase, such as `github.com/owner/name`, with the folder's place inside the repository after `#`. It's read from git's own files without running git; the scheme, user, password or token and port of the remote URL are dropped before anything is saved, and a remote that is a folder or a file isn't saved at all. The database's check takes nothing but that plain shape. It never decides what runs: it only lets the import offer a folder here to that project, which you confirm, and lets this computer move its own folder, when its project is gone, to the one project of the same repository that has no folder here, as happens when another computer merged it (`src/server/project-links.ts`). On macOS, folders where reading would ask for permission (Desktop, Documents, Downloads, iCloud Drive and other cloud drives) aren't read.
- **Sessions PacedMind didn't start, as short summaries.** For the Sessions page on your other computers and in the web app, each computer sends, once a minute, the Claude Code and Codex sessions it finds that PacedMind didn't start (`src/server/other-sessions.ts`), read from the tools' own records without changing them: per session the tool, its id, a title of one line of at most 100 characters (the session's own title, else the start of its first message, so it can hold what you typed there), the name of its folder (never the path), its project, its state and two times. Never the conversation. It goes on the computer's own entry, which only that computer's sign-in may change (the database's trigger), held to 30 entries and 24 KB, and every reader keeps only those fields, as plain text.
- **What a computer tells the account** (the Computers page, on every computer and in the web app): its name and system, that it's still there (every minute), its settings for requests from elsewhere (what it does with them, and whether asking needs a two-factor code), PacedMind's version, and per agent the CLI's and desktop app's versions, whether the app reaches PacedMind, and whether the CLI is signed in (`claude auth status`, `codex login status`) with its method and plan as single words. Never where the tools are, and never an email, an organization, a path or a key: the CLIs' output stays on the computer. The settings are for display, except that the database takes requests without a code only for a computer whose entry says it may; the computer never reads them back, and checks its own settings for every request.

### Agents

- **Startup monitoring reads local status only.** While this computer's terminal sessions are live, PacedMind reads bounded sections of Codex's own session records, from its configured sessions directory. It associates a conversation by its known id or the exact PacedMind kickoff in a user message, ignores ambiguous matches, and records only fixed descriptions of lifecycle and failure categories. It never copies transcript text or raw errors to Cloud, takes control of a conversation, answers startup choices, or switches the model. Missing check-ins and app messages waiting to be sent also produce attention notices. A retry without an identified Codex conversation starts this task afresh instead of resuming another conversation with `--last`.

- **Each session gets its own MCP token.** It can read, add open tasks, edit its own task's details, report with `start_task`/`report_progress`/`finish_task`, and ask you with `ask_user`; it can't see or call anything else (no deleting, settings, other tasks' status, or starting sessions), whatever it is asked to do. The agent needs the token in its session's own config files while it runs; they're deleted when the session ends, and PacedMind itself keeps only a hash. The token stops working when the agent calls `finish_task`, when you mark the task done or close the session, when the agent exits (Claude Code's and Codex's `SessionEnd` hooks, and for Codex the session's start script once `codex` returns), when this computer signs out, and after 24 hours at the latest (for a terminal killed before either could say so). A launched Codex session sends only that token: Settings → **Connect** puts the owner token in `config.toml` as a header, and the launcher clears the header for the session.
- **The session's hooks carry the same token.** Claude Code's hooks (when its turn ends, or an error from the API ends it, when it asks for permission or input, after your message and each tool call, and when it exits) post to the session's own routes (`/api/sessions/<id>/ended`, `/signal` and `/permission`) with the session's token: Claude Code sends them itself (http hooks), and older versions run curl with the token in its arguments. Codex's `notify`, and its hooks (the same events, from Codex 0.150), run curl with the token read from a header file in the session's folder, not on its command line: the hooks run PacedMind's hook script (`codex-hook.sh`, or `codex-hook.cmd` on Windows, in the data folder), which finds the session's route and header file in the terminal's environment (`PACEDMIND_HOOK_URL`, `PACEDMIND_HOOK_AUTH`), so the hook definitions hold no token and are the same in every session. Codex runs a hook only once you've trusted its definition (it asks *Hooks need review*); PacedMind never answers that for you. The script does nothing in a Codex that PacedMind didn't start, and prints only a permission's decision, since what other hooks print reaches the agent. The routes only record what the session says about itself (waiting, asking, stopped at a usage limit, back at work) and answer without a body whatever happens, since what a UserPromptSubmit hook gets back reaches the agent. A token that no longer works gets the same empty answer on `/signal`, so the hooks of a terminal that stays open after its task was handed back don't fill it with errors.
- **Attaching a session you started yourself changes nothing on the computer.** It only records the session under a task (`src/server/attach.ts`): the conversation id (checked against a pattern before it's ever used on a command line) and, on this computer, the folder's path for display. When PacedMind later resumes it, the folder comes from the agent's own record of that conversation on the computer that resumes it (`conversationFolder()` in `other-sessions.ts`), checked like a project's folder, never from the session's row; PacedMind doesn't answer the folder's trust question for such a folder, since you ran the agent there yourself.
- **Git only reads, and the code stays on the computer.** For the **Files changed** part of a report, PacedMind runs git in a session's folder when the session starts and when the agent hands the task back (`src/server/diff.ts`): only commands that read (`rev-parse`, `diff`, `log`, `rev-list`, `ls-files`, and `hash-object` without writing), with `GIT_OPTIONAL_LOCKS=0` so it never locks the index, and with the settings that make git run another program switched off for them (`core.fsmonitor`, external diff tools, text conversions, signature checks). The folder is the one the launcher resolved from this computer's settings and noted at the start, never one from a session's row. On macOS, folders in Desktop, Documents, Downloads and cloud drives aren't read, since macOS would stop to ask. The report keeps only a summary (commit ids and subjects, file paths, line counts), which goes to the account like the rest of the report; the diff itself, which is your code, stays in the data folder of the computer the session ran on, served only to that computer's own window (`/api/diffs/<id>`, a random id).
- **A session's usage metrics carry its token, and only numbers are kept.** The launcher turns on Claude Code's and Codex's usage metrics (OpenTelemetry) for the sessions it starts, sent to the session's own route (`/api/sessions/<id>/usage`) on this computer with the session's token: Claude Code's from its session settings file, Codex's header from the terminal's environment (`OTEL_EXPORTER_OTLP_METRICS_HEADERS`), never on a command line. Only metrics: no events or logs, so neither your messages nor the agent's are sent. The route reads a few metrics by name (tokens, cost, active time) and the model's name, and drops everything else they carry, such as the account's email, account and organization ids and the terminal, before anything is stored; it takes JSON up to 2 MB and always answers as a collector that took it, so a token that doesn't work learns nothing. When your own settings or the environment already send the agents' telemetry somewhere, the launcher leaves it alone, so PacedMind never receives what you meant for your own collector.
- **Answering an agent from elsewhere is off unless you switch it on, per computer.** A question an agent asks with `ask_user`, and, with **Answer from elsewhere** on (Settings → Starting sessions, off by default, only with an account), a tool Claude Code asks your permission for (its PermissionRequest hook, `/api/sessions/<id>/permission`, with the session's token), wait for you in PacedMind (`src/server/asks.ts`): on the task, in Sessions and as a notification. Claude Code asks in its terminal at the same time, and the first answer counts. Each is a `session_asks` row that only the session's computer's own sign-in creates, for a session that runs there, and only it withdraws. An answer comes once, before the agent stops waiting (10 minutes for a permission, 30 for a question): from that computer, or from anywhere else with a two-factor code from the last five minutes, which the database checks (a trigger that refuses every other change to a waiting ask). The computer checks its own setting again before it passes on an answer from elsewhere, so switching it off stops them at once. Only the answer crosses: allow or deny for the one tool call Claude Code asked about, never a rule, a command or a folder, or, for a question, text the agent reads as your reply.
- **The MCP server is called `pacedmind`.** Its earlier name, `organizer`, may still be in your own Claude Code settings with the owner token. A launched Claude Code session's MCP config replaces that entry with one that reaches nothing (port 9 on this computer), and a Codex session has it switched off, so a session never sends the owner token; **Connect** renames the entry.
- **An agent doesn't inherit a Claude Code session PacedMind runs in.** When PacedMind itself runs inside Claude Code (`npm run dev` there, say), the variables that session sets for its programs (its messaging token and ids, `CLAUDE_CODE_CHILD_SESSION`) are removed from the agent's environment and cleared again in its terminal script (`HOST_SESSION_VARS` in `src/server/shell.ts`).
- **Picking a project's MCP servers narrows what its sessions get.** Settings can limit a project's sessions to some of the MCP servers Claude Code and Codex have on this computer. The choice is a list of names in this computer's settings (`device.ts`); the launcher reads the servers' definitions from Claude Code's own files when a session starts (a folder's `.mcp.json` server only once you allowed it in Claude Code) and writes them to the session's config file, which only you can read and which is deleted with the session. Claude Code then runs with `--strict-mcp-config`, Codex with the others switched off. Nothing about them goes to the cloud but their names (below).
- **Your own agents** (Claude Code or Codex you start yourself) use PacedMind Cloud's MCP server once you have an account (below), and without one the owner token from Settings. They can use every tool, but `start_session` and `request_changes` only ask: through the desktop app nothing opens until you click **Allow** in the app, and it refuses if the task, agent or folder changed after you saw the request; through PacedMind Cloud they only return a link, where starting needs your fresh code.
- **Sessions in the Claude and Codex desktop apps** use the same entry as your own agents: the apps read PacedMind from their own settings (**Connect** in Settings), which can't hold a token per session. PacedMind opens the app with the first message written but not sent, so nothing runs until you send it; after that, the agent has your agents' rights, not a session's.
- **Trusting a folder is answered for you, unless you switch it off.** Claude Code and Codex ask whether you trust a folder the first time they start there, and a yes also lets them use that folder's own settings, hooks and MCP servers. With **Trust session folders** on (Settings → Starting sessions, on by default, per computer), the launcher says yes just before it starts a session, for that session's folder only: a project's or task's folder set in this computer's window, or the task's own scratch folder, never a folder from the cloud. It writes that one answer and nothing else: `projects[folder].hasTrustDialogAccepted` in Claude Code's `~/.claude.json` (`src/server/claude-trust.ts`), and `trust_level = "trusted"` for the folder's repository in Codex's `config.toml` (`src/server/codex-trust.ts`), where a folder Codex was told not to trust stays that way. Each file is written next to itself and moved over, keeping its link and permissions. Only give projects folders whose settings and hooks you'd let an agent run; switched off, PacedMind only reads `~/.claude.json` to tell you the question is coming.
- **What a session has is read from Claude Code's own record.** For a Claude Code session PacedMind started in a terminal, `src/server/session-mcp.ts` reads that session's transcript, read-only, for the MCP servers it has tools from and the ones that failed, wait for sign-in or are still connecting. Only names and Claude Code's error codes leave it, never an error's text, which can hold paths. The names of the claude.ai connectors those sessions got (not the connectors' contents) go on this computer's entry in the account's list, where the computer's own sign-in alone may change them, like the rest of what it reports.
- **What the agents have is read, never run.** The Computers page and Settings show which MCP servers, plugins, skills and hooks Claude Code and Codex give their sessions (`src/server/extras.ts`). PacedMind reads that from their config files; it never runs `claude mcp list` or anything else that would start a server, since a folder's servers run code from that folder. Only names leave those files: a server's command, address, headers and environment can hold keys. The account's list of computers gets the names of what each computer's agents have everywhere (never a folder's), kept under the row's size limit.
- **Images an agent attaches** are read from this computer only: a network path (`\\server\share`) is refused before Windows would sign in to that server as you.
- **An area's own picture** (a company logo, say) never reaches the server as the file you picked. The browser draws it into a small PNG, so an SVG's scripts or markup don't survive. The server, and in the cloud the database's check, take nothing but base64 of a PNG of 64 pixels at most and about 24 KB (`src/lib/area-picture.ts`). `/api/areas/[id]/picture` serves it as `image/png` with `nosniff`, from the store in use, so another account's area is never found.
- **MCP refuses browsers.** Requests carrying an `Origin` header are refused, by the desktop app's server and by PacedMind Cloud's.

### Agents signed in to PacedMind Cloud

With an account, agents reach the account through PacedMind Cloud's MCP server (`https://app.pacedmind.com/api/mcp`, the hosted app, `src/server/auth.ts`), from any computer, without a token in their settings: each one signs in with OAuth through Supabase Auth's OAuth 2.1 server, registering itself (dynamic client registration), and you allow it on PacedMind's consent page (`/oauth/consent`).

- **Supabase's consent alone gets an agent nothing.** Every OAuth sign-in needs an explicit approval on PacedMind's consent page. Eligible human planner sessions can approve it, including unenrolled accounts. The approval binds only after code exchange, to exactly one matching client session in the approval window (`private.bind_agent_logins`). Racing sign-ins are revoked. A server-written `mfa_approved` records whether the approval came from established MFA; its value cannot be set or changed by the client. Old approvals retain their existing access. Enabling MFA later never upgrades a basic approval: reconnecting from an established MFA sign-in is required.
- **An agent is never a person's session.** `private.session_ok()` and `private.recent_mfa()` refuse OAuth sign-ins, so an agent that talked you out of a code and verified it with its own token still can't do what needs a two-factor session or a fresh code.
- **What an agent may touch.** An approved agent reads and changes planning data (areas, projects, tasks, events, dependencies, sessions, reports, settings and preferences) and reads computer metadata. It cannot mutate computers, answer tool permissions, read push keys, approve agents or delete the account. Only `private.agent_computer_ok()` approvals may request launches or folders; basic approvals are denied even when a computer has `remote_code=false`. The computer's own request and approval settings still apply. Hosted MCP has no computer files (`attach_image` and images in `finish_task` are unavailable).
- **The server checks too.** It verifies the token with Supabase, refuses a browser's session (no OAuth client) and one without an approval (401 with where to sign in, RFC 9728), and runs every query with the agent's own token, so row level security answers as the agent, never as a browser.
- **Ending it.** **Disconnect** in Settings → Connected agents deletes every auth session of that agent's client (`revoke_agent_login`), so all their tokens stop working at once, and revokes Supabase's consent, so it asks again with full details. Signing out everywhere, the session time limits and deleting the account end every agent's sign-in too.
- **The consent page** shows the agent's name as it registered itself (plain text, never trusted) and where its sign-in returns to, warns when that isn't this computer, and sends the browser back only to the authorization's own redirect address. Only allow a request you started yourself: an agent you allow acts as you in the account, like the owner token does on your computer.
- **Local sign-in completion.** Only the hosted consent page uses `Cross-Origin-Opener-Policy: same-origin-allow-popups`, to keep a handle to the temporary HTTP(S) loopback callback window opened by **Allow**. It closes that window only after `connected_agents` confirms the exact approval has a bound sign-in, or the sign-in has ended. The callback remains a browser navigation to the validated address, never a server-side fetch; hosted callbacks and blocked popups keep the normal redirect. Every other page retains `same-origin` opener isolation.
- The server instructions tell agents that task text is the user's notes, not instructions.

### Starting sessions

| Started by | What happens |
|---|---|
| You, in the desktop app | Starts right away without an account; with Cloud, requires established MFA. |
| An agent over this computer's MCP server | Waits for you to allow it in the app (a notification too). Expires after 10 minutes. |
| An agent elsewhere (signed in to PacedMind Cloud, or on another computer) | A request like one from the web app, marked as an agent's, for a new session only. The OAuth connection must have been approved under established MFA. An agent never counts as having a two-factor code, even one it verified itself or one entered in the desktop app it asked through, so only a computer whose **Two-factor code** is off takes it. Then the computer's own setting decides, as for any request without a code: **Refuse**, **Ask me** or **Start**. The agent reads only its own requests. |
| The web app or another computer | Starting a session, resuming one, or sending one back to its agent with changes. Needs a live two-factor session of the account (never an agent's sign-in) and a fresh two-factor code (checked by the database, as above), unless the computer's own **Two-factor code** setting is off. Then the computer's own setting decides: **Refuse**, **Ask me** (the default: waits for you there), or **Start**, except that anything in the agent's cloud (a session sent there, or one pulled back in) always asks. Expires after 10 minutes; at most ten wait; each request is acted on once. |

**Taking requests without a code** is each computer's own choice (**Two-factor code** under Settings → General, or its card in Settings → Computers; on by default). Only that computer's window changes it (`remoteCode` in `device.ts`); the computer copies it to its entry (`devices.remote_code`), which only its own sign-in may change, and the database's insert policy on `launch_requests` takes a request without a fresh code only for a signed-in computer of the same account whose entry says so (`private.takes_requests_without_code`). A stolen browser session can't switch the code off first, and agents never pass the two-factor session check. The database records whether each request came with a fresh code (`fresh_code`, set by a trigger, which no caller can set or change), and the computer refuses one that came without while its own setting asks for a code, so switching the code back on counts at once, before its entry has caught up. A session started without a code says so in its history.

Every request you're asked about shows the task, the agent, where it runs and the folder (and for changes, what should change), and acting refuses if any of them changed in between. A Claude Code or Codex conversation stays on the computer that ran it, so a request to resume a session or send it back goes only there: the database refuses one for a session of another task, agent, computer or account, and the computer checks again that the session is its own and can be reopened. What should change is your note to the agent: it goes on the session's report, where the agent reads it through `start_task`, and never onto a command line.

**The Computers page** lists the computers signed in to the account. Signing one out deletes its session in the database: it can't read anything from that moment, and within a minute it signs itself out and its agents lose access.

## What you need to set in Supabase

The database side is applied (`supabase/migrations/`). These project settings live outside the database; set them in the dashboard (Authentication), or review and apply `supabase/config.toml` with `npx supabase login`, `npx supabase link --project-ref pyoynjoyhpolijlvoalu` (PacedMind Cloud's project; your own project's ref if you run one) and `npx supabase config push` (it shows the differences first; items marked *dashboard only* aren't in the file).

1. **Multi-factor: TOTP on** (enroll and verify). It's on by default; never push a `config.toml` with it off.
2. **Email: confirm email on.**
3. **Passwords:** minimum length 12; **leaked password protection on** (*dashboard only*, Pro plan); **require current password when updating it on** (*dashboard only*). PacedMind sends the current password, but until this is on Supabase ignores it, and a stolen session could change the password by calling Supabase directly. Reset links keep working: Supabase skips the check in a reset link's session. Leave **secure password change** (an emailed nonce) off: PacedMind asks for the current password and a fresh code instead.
4. **Security notifications on:** password changed, email changed, verification method added, verification method removed (Authentication → Emails, or the file's `[auth.email.notification.*]`).
5. **URL configuration:** site URL `https://app.pacedmind.com`; redirect URLs exactly `http://127.0.0.1:4319/auth/callback`, `http://127.0.0.1:4320/auth/callback` and `https://app.pacedmind.com/auth/callback`, with no wildcards.
6. **Sessions** (Pro plan): time-box 30 days and inactivity timeout 14 days, so every computer and browser signs in again, with its code, at least monthly.
7. **Custom SMTP** before anyone else signs up (*dashboard only*): the built-in sender only emails members of your Supabase organization, two emails an hour.
8. **API keys:** the app uses the publishable key; once nothing else needs it, disable the legacy `anon` JWT key (first check the billing functions still start: they fall back to it on projects without the new keys).
9. The security advisor lists the functions the app calls (`register_device`, `claim_device`, `revoke_device`, `delete_account`, `cloud_plan`, `approve_agent_login`, `claim_agent_login`, `revoke_agent_login`, `connected_agents`) as callable by signed-in users. That's intended: each checks the session itself (two-factor, or for `claim_agent_login` the agent's own OAuth sign-in).
10. **Billing:** put Stripe's secret key (a restricted key is enough: Checkout sessions, Customer Portal sessions, subscriptions, prices and webhook endpoints, write; customers, read) in a file only you can read, as `STRIPE_SECRET_KEY=…`; `npm run stripe:setup -- --keys <file> --write` adds the webhook's signing secret and the portal's settings to it, `npm run stripe:prices -- --keys <file> --write` makes the prices, and `npx supabase secrets set --env-file <file>` hands the file to the functions. Deploy the functions with `npx supabase functions deploy billing-checkout billing-portal stripe-webhook` (their `verify_jwt = false` is in `config.toml`: they check the caller themselves). The webhook's endpoint in Stripe is `https://<project>.supabase.co/functions/v1/stripe-webhook`, for `checkout.session.completed` and `customer.subscription.*`.
11. **OAuth server** (Authentication → OAuth Server, or the file's `[auth.oauth_server]`): on, with the authorization path `/oauth/consent` (on the site URL: `https://app.pacedmind.com/oauth/consent`) and dynamic client registration on, for agents signing in to PacedMind Cloud's MCP server. Registration is open to any client by design; what a client gets still needs your explicit approval from an eligible planner session (see "Agents signed in to PacedMind Cloud").

## What's left to you

- **Switching a computer's two-factor code off lets your agents ask it too.** An agent you connected to PacedMind Cloud, or one on another computer, can then ask that computer for sessions, and with **Start** they start at once, in a folder of that computer's, on a task whose text the agent may have written. Keep the code on for any computer where you wouldn't let an agent start another agent without you.
- **Folders come only from each computer's window.** An agent or another computer can ask one to use a folder for a project, an area or a task (`folder_requests`, or an approval here for an agent on this computer's own MCP server). The request is only a suggestion of at most 1000 plain characters: the computer checks the folder exists there and is safe for a terminal, shows it to you, and sets it only when you allow it; only that computer's own sign-in settles the request, once. Read the path before you allow it: sessions for that project, area or task start there.
- **"Start" for requests from elsewhere trusts the cloud's code check,** for resuming sessions and sending them back with changes too. Keep **Ask me** unless you need to start sessions while away from the computer.
- **Switching a computer's two-factor code off trusts established MFA sign-ins of your account.** Any browser or computer signed in with a factor that predates that sign-in, until it signs out or its session times out, can then ask that computer for sessions; with **Start** as well, someone holding a stolen browser session could start an agent in one of that computer's project folders right away, with a task description they wrote. The agent's own permission prompts still stop it in its terminal, and nobody can answer them from elsewhere without a code. Leave the code on unless you often start sessions from your phone or another computer, and never combine both on a computer where an agent runs without asking permission.
- **"Answer from elsewhere" trusts it too,** for allowing a tool call Claude Code asked about on that computer. Keep it off unless you need to answer agents while away from the computer.
- **Task text is input to an agent.** A task's description can try to talk an agent into something (prompt injection). PacedMind limits what a session can do inside PacedMind; what it can do on your computer is up to the agent's own permission settings.
- **Programs running as you** can read what you can: the running sessions' config files, and `~/.claude.json`, which holds the owner token once Claude Code is connected. If the token leaks, make a new one in Settings; it can't start a session without your click.
- **Right after setting up two-factor sign-in,** controlling computers (including local Cloud launches) or deleting the account asks you to sign out and in again once, because the authenticator you just added is newer than that sign-in.
- **Losing every authenticator locks the account.** Backup codes aren't available on hosted Supabase projects yet, so keep two authenticators. The project's owner can remove a factor in the Supabase dashboard (Authentication → Users).
- **Guessing codes** is limited by Supabase's rate limits. Locking an account after failed codes needs the MFA verification hook, which is on the Team plan.
- **Sign-up and sign-in have no CAPTCHA.** The web app (app.pacedmind.com, run with `ORGANIZER_MODE=web`, `ORGANIZER_PUBLIC_ORIGIN` and `TZ` from `deploy/pacedmind-web.service`) relies on Supabase's rate limits; a CAPTCHA (Turnstile) would also slow down automated sign-ups.
