# Google Calendar setup

The implementation uses Google's OAuth authorization-code flow with PKCE, offline access and multiple editable calendars from multiple Google accounts per planner. It never uses the Google sign-in session from Supabase and never asks a user for an access token.

1. In the Google Cloud project that will own PacedMind's integration, enable **Google Calendar API** and configure the OAuth consent screen. Add the scopes `https://www.googleapis.com/auth/calendar.events` and `https://www.googleapis.com/auth/calendar.calendarlist.readonly`. During testing add the intended users as test users. Follow Google's publication/verification requirements before public distribution. Refresh tokens for an external consent screen in Testing can expire after seven days.
2. Create separate OAuth clients for the hosted web app and installed desktop app. For web use **Web application**, with the exact redirect `https://app.pacedmind.com/api/google-calendar/callback` (or your configured public origin). For development use the exact `http://127.0.0.1:4320/api/google-calendar/callback`. For installed apps use **Desktop app**, loopback redirect `http://127.0.0.1:4319/api/google-calendar/callback`, and PKCE. Do not distribute a confidential web client secret in a desktop installer.
3. Set `GOOGLE_CALENDAR_CLIENT_ID` and, for a confidential web client, `GOOGLE_CALENDAR_CLIENT_SECRET` in the server environment. Development can use `.env.local`. The desktop distribution includes its public client ID in `src/lib/google-calendar-client.json`; environment variables can override it for a custom deployment. Set `GOOGLE_CALENDAR_DESKTOP_CREDENTIALS` to an external JSON file downloaded for a **Desktop app** client when building. The packager includes only that installed-app client ID/secret in the artifact, and the launcher supplies them to its server. Release builds require this file. Keep it out of git. Google requires the installed-app secret at the token endpoint even with PKCE; it is public application metadata, not a confidential web credential. Never bundle a web client secret. These settings are independent of Supabase's Google sign-in provider.
4. Web mode also needs `GOOGLE_CALENDAR_ENCRYPTION_KEY`: 32 random bytes encoded as base64, persisted in secret storage and shared by web replicas. Generate it once with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`. Never commit it. Desktop uses its existing OS-keychain-backed `ORGANIZER_DATA_KEY`; development generates a key under its own data directory. Changing the key makes previous connections unreadable and requires disconnect/reconnect.
5. Apply `supabase/migrations/20261026091622_google_calendar_sync.sql` to the intended Cloud database through the normal migration process. Local SQLite migrates automatically. The migration adds event metadata and an encrypted, per-user connection row with human-only RLS and compare-and-swap revisions. It does not need a service-role key.
6. Restart the server and connect through **Settings → Google Calendar**. Add Google accounts and choose editable calendars. The first calendar becomes the default destination for new PacedMind activities; it can be changed in Settings. Explicitly choose whether pre-existing, unlinked PacedMind activities should be sent when adding the first calendar. Imported events stay with their source calendar; they are never copied across accounts. Removing one connection preserves its events and leaves the others active. The initial sync imports all regular Google events, including history; it is not date-window limited. For very large calendars the initial import can take multiple minutes and is checkpointed/retried.

## Runtime and boundaries

Desktop sync runs every minute while the app is running and its current planner account can write. Web sync is requested by an open tab through a same-origin POST, using the person's current session. There is deliberately no stored Supabase refresh token or privileged cross-account worker. The encrypted connection collection belongs to the host that encrypted it; other computers see that it runs elsewhere and can disconnect it. Browser tab suspension pauses web sync; use the desktop app for continuous background operation.

Google watch channels are not required: incremental `syncToken` polling avoids a publicly reachable desktop webhook and expiring-channel maintenance. A `410` triggers a complete reread without deleting the local planner. `If-Match` protects Google updates/deletions; local compare-and-swap protects concurrent edits. Stable provider IDs and local source tags recover interrupted imports/exports. Conflicting fields pause only that event and expose both versions for a user decision.

Tokens and sync metadata are AES-256-GCM encrypted, bound to the planner's account ID. The versioned payload upgrades existing single-calendar connections in place, preserving credentials and mappings without a schema migration. The connection table is inaccessible to OAuth agents, other users and anonymous requests. No token appears in UI props, logs, URLs or responses. The callback accepts only a ten-minute, single-use state plus the matching PKCE verifier. Google settings are stripped from child-agent environments and reusable terminal scripts. No new callback bypass is granted to other routes.

Supported fields: title, start/end, IANA timezone, all-day, description, location, RFC5545 repeating series and Google exceptions. The UI edits an entire series; individual exception creation/cancellation is done in Google. Google guests/notifications, Meet, attachments and special event types are not managed. Disconnect deletes authorization locally, preserving events; revoke the Google grant in Google account settings if desired. Data reset/restore disconnects before replacing events. Copies and account transfers preserve event metadata but do not activate a copied connection.

## Verification

Run `npm run test:calendar`, `npm run test:sql`, `npm run test:i18n`, `npm run typecheck` and `npm run build`. On hosts with limited compiler memory, run SQL checks with `node --wasm-num-compilation-tasks=1 scripts/test-sql-security.mjs`.

Before release, use a dedicated Google test calendar to verify actual OAuth consent/refresh, initial import, edits/deletes in both apps, a DST-crossing recurring series, a moved and cancelled occurrence, simultaneous edits and disconnect. The automated HTTP tests mock Google; they do not attest Google Cloud consent configuration or a live account connection.

Primary references: [OAuth web flow](https://developers.google.com/identity/protocols/oauth2/web-server), [installed apps](https://developers.google.com/identity/protocols/oauth2/native-app), [incremental synchronization](https://developers.google.com/workspace/calendar/api/guides/sync), [conditional changes](https://developers.google.com/workspace/calendar/api/guides/version-resources).
