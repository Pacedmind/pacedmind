# Organizer

The user-facing brand is **PacedMind**. Keep the `Organizer` install/data paths, Windows app ID
and environment variables for compatibility. The MCP server is `pacedmind` (`MCP_NAME` in `src/lib/types.ts`); its old
name `organizer` (`OLD_MCP_NAME`) still counts as connected, Connect replaces it, and launched sessions override it. Brand assets are in `public/brand/`;
the original approved PNG stays unchanged as an archive. `src/lib/brand-geometry.json` defines
the active wordmark's crop and animation bounds; `npm run icons` exports the solid connected-pd emblem and icons.

A personal, Linear-style planner (tasks, time blocks, calendar, deadlines) that also coordinates Claude Code and Codex sessions. Organizer only tracks state: the user talks to agents in their own terminals, and agents report back over MCP.

## Run

- Data lives in one of two stores. Without an account (the free One device plan), the desktop app keeps this computer's own data in SQLite (`organizer.db` in its data folder, through `node:sqlite`). Signed in to PacedMind Cloud, it uses the account's data in Supabase (Postgres + Auth), PacedMind's project `pyoynjoyhpolijlvoalu`; signing out switches back. The cloud schema, row level security, triggers and functions are in `supabase/migrations/` (applied through the Supabase MCP or `npx supabase db push`); `supabase/tests/security.sql` checks the rules and rolls itself back. Read `SECURITY.md` before touching auth, the launcher, MCP or the schema.
- Cloud accounts may defer two-factor setup. `private.planner_session_ok()` allows a live human aal1 session only while the account has no verified factor; enrolled accounts must verify MFA. Computer access uses `private.computer_session_ok()` (aal2 and a factor older than the sign-in), checked by `can_control_computers()` in the launcher/actions/MCP and by RLS. OAuth approvals without established MFA remain planner-only until reconnected. See `supabase/tests/optional_mfa.sql` and `npm run test:sql`.
- `npm run dev` serves the app and the MCP server at http://127.0.0.1:4320 (bound to localhost only). Only the app's own window may use it (`src/server/ui-key.ts`): open the unlock link the server prints once. Without signing in it uses `data/organizer.db`, created with sample data on first start (Settings → Data resets it); signing in uses PacedMind's Supabase project unless `.env.local` names another (see `.env.example`; `npx supabase start` runs a local stack). Its session, device settings and tokens are plain files in `data/`, for development only.
- `npm run desktop` builds the Electron app and installs it for the user (`scripts/build-desktop.mjs`): on Windows in `%LOCALAPPDATA%\Programs\Organizer`, on macOS as `~/Applications/PacedMind.app`. The app runs `.next/standalone/server.js` with Electron's own Node on port 4319 and hands it two keys: a window key made each run (a cookie in its window, a header from its main process) and a data key kept in the OS keychain (`safeStorage`), which encrypts `session.json` and `device.json` in its data folder (`%APPDATA%\Organizer\data`; macOS: `~/Library/Application Support/Organizer/data`). Without an account the app keeps its data in `organizer.db` there, starting empty (`ORGANIZER_SEED=empty`); once you're signed in, Settings → Data moves it into the account. Dev and app never share a port or a data folder.
- `npm run release` builds the downloadable installer for the system it runs on (Windows NSIS, or a signed and notarized macOS DMG) and uploads it to the VPS (`scripts/release.mjs`, deploy/README.md).
- Several sessions work at once, each in its own worktree, and the installed app, the downloads and the server take whatever the checkout that builds them holds. So work lands on master first (commit, merge master into the branch, fast-forward master), and only a checkout that contains master builds them: `npm run desktop` refuses one that doesn't, and `npm run release` and `deploy/deploy.sh` also refuse uncommitted changes (`scripts/landed.mjs`; `--allow-unlanded`, or `ALLOW_UNLANDED=1` for deploy.sh, only for a test).
- Two modes (`MODE` in `src/server/supabase.ts`). `desktop` (the default; the desktop app and `npm run dev`): one signed-in account per server, or none (this computer's own data), whose data every part of the server uses (pages, MCP calls from agents, session hooks, the background loop); it starts agent sessions and serves MCP. `web` (`ORGANIZER_MODE=web` and `ORGANIZER_PUBLIC_ORIGIN`, the hosted app): a session per browser in HttpOnly cookies; no sessions. Its MCP server is PacedMind Cloud's, for agents signed in with OAuth (below). Every session runs on one of your computers: "Start", "Resume" and "Request changes" there ask one (a `launch_requests` row of kind `start`, `resume` or `changes`, which the database only accepts with a two-factor code from the last five minutes, unless that computer switched its code off (`remoteCode` in `device.ts`, copied to `devices.remote_code`; `fresh_code` records whether a request came with one, and the computer refuses one without while its own setting asks), and for resume and changes only for a session that ran on that computer), and that desktop app refuses it, asks you, or does it, as its own setting says (anything in the agent's cloud always asks). The desktop app asks the same way for a task or session that belongs to another computer. The actions answer `remote` with the computer to offer (the task's, else its project's, else the account's default; for a session, the one it ran on), and the page sends the request (`requestSessionAction`, `requestResumeAction`, `requestChangesRemoteAction`). An agent's `start_session` asks a computer the same way, for a new session only: `requested_via` `agent` (the database sets it for an approved agent, which then reads only its own requests), never with a fresh code, so only a computer whose code is switched off takes one, and that computer's setting decides as for any request without a code (`handle()` in `requests.ts`).
- `npm run typecheck` generates route types and runs `tsc`. `npm run icons` redraws the icons. `npm run screenshots` retakes the docs' screenshots and the website's hero screens (`-- docs` or `-- site` for one of them): a development server of its own on the sample data, with an empty home so nothing of this computer shows, and its clock at 10:40 today (`scripts/screenshots*.{mjs,cjs}`).

## Layout

- `src/server/` is server-only:
  - `supabase.ts` (the clients, `MODE`, `authState`/`readAuthState`, `requireAal2`), `supabase-config.ts` (project URL, publishable key, cookie options), `auth-flow.ts` (the sign-in steps), `step-up.ts` (fresh two-factor codes);
  - `repo.ts`: every data function, async. Each call goes to the store in use (`scope.ts`, which also gives `activeDevice()`): `store/cloud.ts` (the signed-in account's, in Supabase) or `store/local.ts` with `store/local-db.ts` (this computer's own: schema, sample data, reset). `store/shared.ts` has their shared shapes and rules. Both merge this computer's project and task folders into `Project` and `Task`;
  - `account.ts`: resetting the account, its sample data, moving this computer's own data into it, and the account's back to this computer (`moveToThisComputer`, Settings → Data → **Move to this computer**, which then signs out);
  - `device.ts` (what this computer decides for itself: agent commands, terminal, project and task folders, which MCP servers each project's sessions get, the settings for requests from elsewhere (`remoteStart`, and `remoteCode`: whether they need a two-factor code), the owner MCP token and per-session tokens, and whether it opens without an account), `secure-file.ts` (encrypted JSON files), `ui-key.ts` and `window.ts` (the window key), `guard.ts` (`guardAction()`, first line of every Server Action);
  - `devices.ts`: this computer among the account's computers. It looks for the Claude Code and Codex CLIs, their desktop apps, their MCP config, whether each CLI is signed in (`claude auth status --json`, `codex login status`: the state, and the method and plan as single words) and what else their sessions get (`extras.ts`) at start and every half hour, keeps what it found for starting sessions here, and saves a copy without paths, emails or keys to its `devices` row, which the Settings → Computers page (`src/components/computers-settings.tsx`, `views/computers.tsx`: rename, default, sign out, what each computer can run, its settings for requests from elsewhere (changed only on that computer; their words in `src/lib/from-elsewhere.ts`), its sessions) shows on every computer and in the web app. `thisDevice()` is this computer in both stores (the only one without an account); `offeredDevice()` picks the computer to offer for a task. A computer is online when its `lastSeenAt` is under two minutes old (`deviceOnline()` in `src/lib/types.ts`); it writes it every minute;
  - `asks.ts`: what a running session's agent waits for you to answer (`session_asks`): a question from `ask_user`, or with "Answer from elsewhere" on a tool Claude Code asks permission for (its PermissionRequest hook, `src/app/api/sessions/[id]/permission`, held up to ten minutes while its terminal asks too; the hooks that follow an answer there end the hold). Answered in the window (`AskCard` in `src/components/ask-card.tsx`), or from elsewhere with a fresh code (the database checks it, and this computer its setting). `push.ts`: web push, sent by the computer a session runs on to the account's browsers (`push_subscriptions`) with the account's VAPID keys (`push_keys`), for the session events that need you (`repo.addSessionEvent`); `public/sw.js` shows them, `src/app/manifest.ts` lets phones install the web app, and `src/components/push-settings.tsx` is the Settings part;
  - `launcher.ts` (starts a session in a terminal, the agent's desktop app or its cloud; treats everything from the cloud as untrusted), `requests.ts` (approvals; launch requests of each kind, decided by this computer's setting; registering this computer, keeping its entry current (last seen, a name given elsewhere, its version) and noticing when it was signed out elsewhere), `folder-requests.ts` (folders asked for over MCP or from elsewhere, for a project, an area or a task: each computer's own setting, so the request waits in that computer's window, which checks the folder and sets it once you allow it; `folder_requests` in the cloud, which only the computer asked picks up and settles), `dependencies.ts` (which open task of a project is ready, for `get_next_task`), `preferences.ts` (how the user likes to work: `changePreferences` for Settings → How you work and `update_preferences`, and the text agents get), `background.ts` (the loop), `auth.ts` (who an MCP request acts for), `connect.ts` (Settings' "Connect" for Claude Code and Codex: with an account PacedMind Cloud's MCP server, which the agent signs in to itself in a terminal `openMcpLogin` opens; without one this computer's with the owner token. The layout offers it once after signing in, `cloud-connect-offer.tsx`; the web app instead shows each agent's steps, as pacedmind.com/connect has them, until the account has an agent connected or the browser said Not now, `agent-connect-card.tsx` and `CONNECT_CARD_COOKIE`), `views.ts` (view helpers);
  - `marker.ts`: `pacedmind.md`, which signed in the app writes into a folder linked to a project or made an area's workspace (`markProject`/`markArea`, from every place that links one; `markAll` for Settings → Projects' Add pacedmind.md). Its header names them by the account's ids, so another computer recognises its clone by it (`markedAround` scans the found folders and those next to and inside this computer's project and area folders); its text points agents to the tasks. It never decides anything by itself: `folder-hints.ts` and `import.ts` rank a marker match first (`FoundFolder.how`), the layout's `LinkOffer` (`link-offer.tsx`) offers the sure matches for one click (`linkFoundAction`, `linkWorkspace` in `project-links.ts`, refusals kept in `device.ts` `linkOfferSeen`), and the import lists area workspaces too (`findWorkspacesAction`).
  - `import.ts`: `findWork` finds the folders you work in with Claude Code and Codex on this computer (their own session records and configs, read-only) and the git repositories in and around them (two levels down, not hidden folders or worktrees), as areas and projects: a folder that isn't a repository but holds some is an area and each folder in it a project (a repository, or a folder of several repositories that is one project); a folder near the top whose folders are areas is a folder of areas; areas don't nest. Each area and project joins one you have when it can (pacedmind.md, repository, for an area the area of the projects in it (two or more agreeing), name: `FoundArea.joins`, `FoundProject.joins`), else it's new; `importAreas` and `importProjects` set them up for the import (`importProjectsAction`);
  - `attach.ts`: attaching one of those sessions to a task (Sessions → the link button, `attachSessionAction`): it becomes a session of the task with the same conversation (`cliSessionId`, `outsideConversation()` in `src/lib/types.ts`), running or finished by its state, on the computer it runs on, and leaves the list (`scanOtherSessions` skips conversations PacedMind's sessions have). Resume and Request changes open a session in the folder its conversation ran in (`conversationFolder()` in `other-sessions.ts`, from the agent's own record on this computer; the task's when that's gone), since Claude Code finds a conversation only from there;
  - `other-sessions.ts`: the Claude Code and Codex sessions on this computer that PacedMind didn't start (Claude Code's transcripts, the Claude app's Code sessions, Codex's rollouts; only a transcript's first and last 64 KB, and programs' runs through the SDK left out), as `OtherSession`: title, folder name, project, state, times. `session-list.ts` (`otherSessionGroups`) shows this computer's as found and the others' from their `devices.other_sessions`, which `requests.ts` sends once a minute (times to five minutes, only when changed);
  - `git-remote.ts`: which repository a folder holds (`Project.repo` and `Area.repo`, host/path of its remote, the same on every computer; `repoLink()` in `src/lib/types.ts` makes the link `RepoLink` shows on project and area pages), read from git's files without running git; on macOS never inside Desktop, Documents, Downloads or cloud drives, where a read waits for a permission prompt. `project-links.ts`: fills in `repo` for projects with a folder here and moves this computer's folder after a merge elsewhere (every minute, `background.ts`), links a folder to a project (`linkFolder`, which also unpins a project pinned to another computer), and merges projects (`mergeProjects`, with `repo.mergeProject` in both stores). An area's repository comes from its workspace (`setAreaFolderAction`, and `linkProjects` for workspaces set before), and `foldersOfRepos` in `import.ts` finds this computer's copies of it for the area's workspace picker (Settings → Projects); nothing sets a workspace by itself;
  - `claude-trust.ts`: whether Claude Code will first ask if you trust a session's folder, read from its `~/.claude.json`, for the hints in the task details, Sessions and the launcher's messages; and `trustForClaude`, which the launcher calls just before a session starts when the computer's **Trust session folders** is on (`trustFolders` in `device.ts`, the default), with `trustForCodex` (`codex-trust.ts`, Codex's `config.toml`) for Codex. They write only that folder's answer, into the file as it is, next to it and moved over. A yes also turns on the folder's own hooks and MCP servers, so never answer for a folder that didn't come from this computer's own settings;
  - `signals.ts`: what the hooks in a session's terminal say (`/api/sessions/[id]/signal`: its turn ended, it asks for permission or input, you answered, it went on) and MCP activity, turned into session events; `attentionOf()` in `src/lib/dates.ts` reads what a running session waits for you about from its latest event, and `attention.ts` keeps that in memory (every event goes through `repo.addSessionEvent`), so the hook after each tool call answers without reading the store. Also records the MCP client a session connects with;
  - `extras.ts`: what Claude Code and Codex give their sessions besides PacedMind (MCP servers, plugins, skills, hooks), everywhere and in a project's folder, read from their own config files, never by running them; names only leave it. Also the server definitions a project's picked list gives a session (`--strict-mcp-config` for Claude Code, the others switched off for Codex). `session-mcp.ts`: what a Claude Code session PacedMind started actually has from its MCP servers, from the `deferred_tools_delta` records in its transcript (the servers it has tools from, and the ones failed, waiting for sign-in or connecting), recorded at `start_task` as `environment` and `mcp_status` events and looked at again while one is missing; the claude.ai connectors it got go on this computer's entry (`AgentExtras.account`, `noteAccountServers` in `devices.ts`), since each computer's CLI can be signed in to another account;
  - `cloud.ts`: asks `codex cloud list --json` which Codex cloud tasks this computer sent are ready. `shell.ts`: the agents' environment, quoting, running commands and opening links.
- Sign-in: `src/app/login` (sign in, create account, reset password, and in the desktop app "Continue without an account"), `/login/setup` (optional first authenticator, required for computer access), `/login/verify` (the code at every sign-in), `/login/new-password`; `src/app/auth/actions.ts` (sign-in and account security); `src/app/auth/callback` (email links, PKCE only) and `/auth/done`. Signed in, the `(app)` layout asks for a second factor only when one is enrolled; otherwise it offers setup while allowing the planner and MCP. Without an account, the desktop app opens the sign-in screen until "Continue without an account" is chosen (`withoutAccount` in `device.ts`, cleared by every sign-in), then this computer's own data with **Sign in** in the header; every way of signing out returns to the sign-in screen.
- Billing: PacedMind Cloud is a subscription, monthly or yearly (`yearlyMonths` times the monthly price), at a country's price from `site/prices.json`, with 7 days free from sign-up; the One device plan is free. The database keeps each account's plan (`billing`, which only the `stripe-webhook` Edge Function writes) and decides whether the account may still write: once billing is on (`private.billing_switch`, off until launch), a statement trigger refuses inserts and updates with SQLSTATE PT402 after the trial and the subscription end, while reads, deletes and a computer's reports about itself go on. The stores turn PT402 into `CloudReadOnly` (`src/lib/billing.ts`, which MCP tools pass on as their error); `public.cloud_plan()` gives the app the plan (`readPlan()` in `src/server/billing.ts`), `/api/state` carries it (`plan`) for `useAction`'s message, and `src/components/billing.tsx` has the banner. Settings → **Plan** subscribes, switches monthly/yearly and opens the billing page through the `billing-checkout` and `billing-portal` Edge Functions (`supabase/functions/`, Deno, with Stripe's key in Supabase's secrets; the app only calls them with the account's own session). `npm run stripe:prices` makes Stripe's prices match `prices.json`. `billing` has no local table.
- `src/app/api/mcp/route.ts` is the MCP server (`mcp-handler` v2). Every request needs `Authorization: Bearer <token>` and no `Origin` header (`src/server/auth.ts`).
  - In the desktop app: the owner token (Settings → MCP server) or the token of one session PacedMind started, which only gets `SESSION_TOOLS` (`src/server/mcp/agent-tools.ts`) for its own task and stops working when the session ends. `start_session` and `request_changes` only ask: you allow them in the app.
  - In the hosted app, PacedMind Cloud's MCP server (`https://app.pacedmind.com/api/mcp`, `cloudMcpUrl()` in `supabase-config.ts`): agents sign in with OAuth through Supabase Auth's OAuth 2.1 server (dynamic registration). A 401 points them to `/.well-known/oauth-protected-resource/api/mcp`; Supabase sends the sign-in to `src/app/oauth/consent`, where **Allow** records an approval from the two-factor session (`approve_agent_login`) before Supabase's own; it binds to the one sign-in of that client that came of the request once Supabase exchanged its code (`private.bind_agent_logins`, run by the agent's first call, `claim_agent_login`, and by `connected_agents`, which Settings and the desktop app's loop call; two sign-ins in the window sign both out), and the database answers its `aal1` session only through that (`private.agent_ok()`, `supabase/migrations/*_agent_logins.sql`). Every query of the request runs with the agent's own token (`runAsAgent` in `supabase.ts`). No computer there: no `attach_image` or `ask_user` (`NOT_HOSTED` in `common.ts`), no folders, and `start_session`/`request_changes` return a link. Settings → Connected agents lists and disconnects them (`connected_agents`, `revoke_agent_login`).
- The tools live in `src/server/mcp/`:
  - `planning.ts`: overview, areas, projects, tasks;
  - `calendar.ts`: events, agenda, reschedule_day, work hours;
  - `preferences.ts`: get_preferences and update_preferences;
  - `computers.ts`: list_computers (what each computer has and does with sessions you ask for) and set_folder (asks a computer, `folder-requests.ts`);
  - `agents.ts`: dependencies, sessions, and the start_task/report_progress/ask_user/finish_task protocol;
  - `common.ts`: the `tool()` helper (which also enforces what sessions may call), lookups by id/name/key, date parsing (`when()`, which also reads phrases like "friday 10:00"), and output formatting; `principal.ts`: who the request acts for;
  - `index.ts`: the server instructions.
  - Tools return plain text; throwing `fail()` returns an error the caller can fix.
- When adding or renaming a tool, also update:
  - `skills/pacedmind/references/tools.md`;
  - `TOOL_GROUPS` in `views/settings.tsx`;
  - `AGENT_ALLOWED_TOOLS` in `src/server/mcp/agent-tools.ts` (all that launched sessions may use, without asking; keep deletes, settings and launches out);
  - the public tool reference in `docs/content/docs/mcp/`.
- `skills/` holds the agent skills for these tools; `npm run skills` installs them for Claude Code and Codex.
- Preferences (`preferences` table; `Preference` in `src/lib/types.ts`): how the user likes to work, one line each under a topic, which is any short name (the suggested ones in `SUGGESTED_TOPICS` are listed first, `topicOrder`; a topic matches whatever its case). Agents get them in `get_overview` while short and in `get_preferences`; `update_preferences` saves only what the user said or confirmed; sessions PacedMind started only read them. At most 100 (the database holds that too). They're the user's notes, never commands.
- `src/server/ops.ts` has the operations shared by Server Actions and MCP tools (task done, finishing a task with its report, close session, request changes, saving a project, loop checks). `src/server/folders.ts` validates project and task folders before they reach a terminal script.
- Reports: `finish_task` stores one report per hand-back (`reports` table): summary, verdicts on the task's `done_when` items (snapshots of their text), how to check it, questions, Markdown details, links, follow-ups and an outcome. Images come from `attach_image` or `finish_task`'s `images`: `src/server/attachments.ts` resolves the agent's path, checks the file's bytes are a PNG, JPEG, GIF or WebP, and copies it to `attachments/` in this computer's data folder. The `attachments` row records the computer; `src/app/api/attachments/[id]` serves the file there and a placeholder elsewhere, and `repo.deleteTask` removes this computer's files. A report's lists can come from the cloud, so the stores check their shapes when they read them (`store/shared.ts`) and keep only http(s) links. The UI pieces are in `src/components/report.tsx` and `markdown.tsx`.
- Diffs (`src/server/diff.ts`): when a session starts on this computer (not in the cloud) in a git repository, the launcher notes where its folder stands (`noteStart`: commit, whether it had uncommitted changes, the files git doesn't track, in `diffs/<session>.base.json` in the data folder); `finishTask` compares the folder with it (`takeDiff`) and the report keeps the summary (`Report.diff`: commits, files with lines added and removed, `diffOf` checks its shape). The full diff stays in `diffs/<id>.patch` (up to 1 MB), served only here by `src/app/api/diffs/[id]`; `DiffSection` in `report.tsx` shows both. Git only reads, with optional locks off and the settings that run programs switched off; the folder comes from the note, never from a row. On macOS, folders where the system asks first (`asks` in `git-remote.ts`) aren't read.
- Request changes (`requestChanges` in `ops.ts`, the button, and the `request_changes` tool, which only asks: `askForChanges` in `requests.ts`): the user's text goes on the session's last report (`changes`), where `start_task` finds it, and `reopenForChanges` in `launcher.ts` reopens the session. Only terminal sessions can, on the computer they ran on (from anywhere else, a `changes` launch request asks that computer): the apps start new conversations, and cloud sessions can't call `start_task`. Both agents start a new conversation, which `start_task` hands the text and the last report: an interactive Claude Code that resumes a conversation answers its first message before PacedMind's MCP server is back, drops the tools the conversation had, and gives up. The session's `cliSessionId` becomes the new conversation's id. Each conversation has its own `settings-<cli>.json`, whose hooks pass `?cli=`, so a terminal still open on the old conversation says nothing about the session. Answers to a report's questions go the same way (`AnswerForm` in `report.tsx`; the text starts with `ANSWERS_HEADING`, which `start_task` and the history tell apart).
- `src/app/api/sessions/[id]/ended` is called by the Claude Code `SessionEnd` hook that the launcher installs per session, with that session's token, and `src/app/api/sessions/[id]/signal` by its other hooks (Stop, StopFailure, Notification, UserPromptSubmit, PostToolUse; http hooks from Claude Code 2.1.84, curl before) and by Codex's `notify`. StopFailure with `rate_limit` or `billing_error` is the attention kind `limit` ("Paused: usage limit"); Notification's `quota_auto_resume_fired`, your message or its next tool call end it. Codex sessions (0.150 and later) get the same through its hooks, passed with `-c` (`codexHooks()` in `launcher.ts`): the definitions are the same in every session, since Codex runs a hook only once you've trusted its definition (it asks once per computer), and each runs PacedMind's hook script (`codex-hook.sh`/`.cmd` in the data folder), which reads the session's route and header file from `PACEDMIND_HOOK_URL` and `PACEDMIND_HOOK_AUTH` in the terminal. SessionStart (`kind=start`) tells PacedMind the Codex conversation (`cliSessionId`, which resume goes back into, and which tells the session's own turns in `notify` from Codex's side turns); PermissionRequest goes to the permission route, which records it or, with Answer from elsewhere, holds it; the start script reports the end once `codex` returns, for when the hooks aren't trusted yet. Both answer without a body: a UserPromptSubmit hook's answer reaches the agent, and Claude Code reads an http hook's answer as instructions.
- Usage (`src/server/usage-metrics.ts`, `src/app/api/sessions/[id]/usage`): the agents' own usage metrics (OpenTelemetry, OTLP over HTTP as JSON), which the launcher points at the session's usage route with its token: Claude Code through its settings file's `env` (`usageEnv()`), Codex 0.150+ through `-c otel.metrics_exporter` and `OTEL_EXPORTER_OTLP_METRICS_HEADERS` in the terminal (`codexUsage()`); neither when your own settings or the environment already send their telemetry somewhere. The route adds each delta export to `Session.usage` (tokens per conversation, the API price Claude Code counts, working seconds, models) and keeps nothing else. `src/lib/usage.ts` sums it per task (`TaskContext.agentUse`) and formats it for the task panel, the project header, Sessions and MCP.
- `src/app/api/state` returns a version that changes on every write to the data in use, plus the sessions waiting for the user (with their report's outcome and questions), the running sessions whose agent waits for you (`attention`, with the event that says so), (desktop) the requests waiting to be allowed, the account's launch requests of the last half hour (`requests`, `LaunchRequestView` in `src/lib/types.ts`), what running sessions wait for you to answer (`asks`, `AskView`) and until when a code entered in this session still counts (`codeFreshUntil`, a hint: the database decides). Pages poll it to refresh (`live-refresh.tsx`); the desktop app polls it for notifications. `src/app/api/health` says the server is up, for the desktop app starting it.
- `src/proxy.ts` puts a nonce-based Content Security Policy and hardening headers on every response. In the desktop app it rejects requests whose Host isn't 127.0.0.1 or localhost (DNS rebinding) and any request without the window key, except MCP, session hooks and email links; in the hosted app it refreshes the browser's Supabase session cookie and sends signed-out visitors to `/login`.
- `desktop/main.mjs` is the Electron main process: starts the server with its keys, window, tray (the menu bar on macOS), notifications (finished sessions and sessions waiting to be allowed), `--install`/`--uninstall`/`--quit`/`--hidden`. Keep both systems working: Windows-only calls (shortcuts, balloons, the title bar overlay's colors) stay behind `WINDOWS`, and nothing may write into the macOS app bundle, which would break its signature.
- Floating task notes: **Float task** on a task row or its details opens one independent, always-on-top window per task (`desktop/task-windows.mjs`, `src/app/floating/task/[id]`, `floating-task.tsx`). It uses the same window cookie, task completion action and live refresh as the planner. Notes carry their original store scope and task creation time; reads and writes refuse changed accounts or replaced tasks, and `/api/state` tells the desktop to close notes when the scope changes. Closing a note only closes its window. `list_task_note_displays` and `show_task_note` (`mcp/task-notes.ts`) let an agent show notes locally or through Cloud; a launched session is limited to its own task. Multiple screens without a saved choice require a display and an explicit answer about remembering it. The main process remembers that choice per scope in window-state.json, tiles notes with `task-note-layout.mjs`, and polls `/api/desktop/task-notes` with its header key (never the cookie). `task_note_requests` in both stores expires requests after two minutes and claims before delivery; `devices.note_displays` is only that computer's report. `npm run test:notes` checks screen selection, layout and window boundaries; `test:sql` includes `supabase/tests/task_notes.sql`.
- Agent terminals: `launcher.ts` opens Windows Terminal or Command Prompt on Windows, Terminal or iTerm on macOS (a `.command` file opened with `open -a`); the choices live in `src/lib/terminals.ts`.
- `src/app/actions.ts` holds the Server Actions. Every one starts with `guardAction()`, and every mutation ends with `refresh()` from `next/cache`, or the page will not re-render.
- `src/lib/` is shared by client and server: types, dates, colors (`colors.ts`), what a task needs from a computer (`needs.ts`: `Task.needs`, MCP servers or claude.ai connectors by name, matched against what a computer said its agent has, `toolsOn`, with `needKey`; `deviceWithNeeds` picks the computer to offer), the icons an area can show (`area-icons.ts`: Lucide names by category, with words to search them by; `src/components/area-icon-paths.ts` has their shapes; both are made by `scripts/area-icons.mjs`, where the list lives; `AreaMark` in `icons.tsx` shows an area's picture, its icon or its dot; an area's own picture, such as a company logo, is a small PNG the browser draws in the area menu and the area keeps in base64, checked by `area-picture.ts` and served by `/api/areas/[id]/picture`), the quick-add parser (`parse.ts`), the auto-planner (`planner.ts`). The brand marks next to MCP servers and connectors (`ToolIcon` in `src/components/tool-icon.tsx`, matched by name) are Simple Icons paths in `tool-icon-paths.ts`, made by `scripts/tool-icons.mjs`, where the list of brands lives.
- `src/components/` holds the UI kit (`ui.tsx`, `icons.tsx`, `popover.tsx`, `dialog.tsx`), task UI (`task-list`, `task-row`, `task-detail`, `quick-add`), the area/project menus (`entity-menu.tsx`, used by the sidebar and `/projects`), `approvals.tsx` (requests waiting for you, by kind, desktop), `remote-start.tsx` (the "Run on a computer" sheet: starting, resuming or sending changes to a session on one of your computers, from the web app or for a task or session that belongs to another computer) and `request-status.tsx` (what became of those requests, from `/api/state`: waiting, started, refused, expired). Views live in `src/components/views/`.
- Settings is a menu of pages, each at `/settings/<id>`: `src/lib/settings-menu.ts` lists them by group and says which exist with or without an account and in which app; `src/app/(app)/settings/[section]/page.tsx` reads only what the page shows; `views/settings.tsx` has the menu (`SettingsShell`) and one component per page. A new page needs all three. `/settings` alone opens the first page, or the one an old anchor names (`OLD_ANCHORS`).
- Production: the web app at `https://app.pacedmind.com`, the site at `https://pacedmind.com` with the docs under `/docs`, all on one OVH VPS behind Caddy. `deploy/` has the server setup, the deploy script and the steps (`deploy/README.md`).

## Conventions

- Next 16: `params` and `searchParams` are Promises, so use `PageProps<"/route">` and await them. Pages under `src/app/(app)` are dynamic (`force-dynamic` in the group layout): they read the data in use (the account's or this computer's own) on every request.
- Every `repo` function is async, and both stores implement every one (`repo.ts` checks that at compile time): a new data function goes into both. Cloud queries never filter by user: RLS does. A new table needs its schema in `store/local-db.ts` too (with a line in `migrate()` for older files), and in the cloud `user_id uuid not null default auth.uid()`, an "own rows" policy, the restrictive "Two-factor session" policy, references that include `user_id` (composite foreign keys onto `unique (user_id, id)`, so no row can point at another account's rows), checks on its text, no grants to `anon`, and a line in `supabase/tests/security.sql`. Area and project ids are UUIDs in the cloud and slugs locally; task ids are numbers in both, so this computer's task folders are kept apart by store (`TaskScope` in `device.ts`). In the cloud, task keys (WRK-12) come from a database trigger.
- Nothing from the cloud decides what runs on a computer. Agent commands, the terminal, project folders and MCP tokens live in `device.ts`, changed only from the desktop window; the launcher checks task keys and ids against strict patterns before they reach a command line, and never reads a folder or command from a row. The local store's file holds none of them either (an older file's are moved into `device.ts` once, `adopt()` in `store/local-db.ts`, after it saves a copy of the file as `organizer-before-upgrade-<time>.db`). No Supabase secret or service-role key goes anywhere in the app (only the billing webhook, an Edge Function inside Supabase, uses the service role).
- A computer's `devices` row: its name and `is_default` (one per account) change from any two-factor session, and the computer adopts a name given elsewhere; what it reports about itself (`last_seen_at`, `agents`, `checked_at`, `app_version`, the `remote_start` and `remote_code` copies) changes only from its own sign-in (a trigger in the database), so only `syncDevice`, `saveDeviceTools` and this computer's Settings write those. `remote_start` is for display, and `remote_code` only lets the database take requests without a code: the computer never reads them back, and checks its own `device.ts` for every request.
- Server-side "today" uses the server's time zone. That's the user's own in the desktop app; the hosted app must run with `TZ` set (e.g. `Europe/Warsaw`) until settings carry a time zone per account.
- Dates are local strings: `YYYY-MM-DD`, `YYYY-MM-DDTHH:mm`, and timestamps `YYYY-MM-DDTHH:mm:ss`. Use the helpers in `src/lib/dates.ts`.
- Visual rules: use semantic tokens in `globals.css` for both the near-black dark palette and neutral light palette; avoid fixed neutral colors in components. Color means identity (areas and projects). A project's color is its own or its area's: always use `projectColor(p, areas)`. State is grayscale. The navy accent (`--color-accent*` tokens; never a fixed color, so both themes work) is only for today or now, selection, the one primary button, and "session finished, waiting for you". Muted red is only for overdue. The week calendar alone adds a light wash of the agents' colors (`--color-claude`, `--color-codex`) on their sessions and tasks.
- Agent terminals get the server's environment minus its own variables (`agentEnv()` in `shell.ts`): no PORT, NODE_ENV, ELECTRON_RUN_AS_NODE, NEXT_*, ORGANIZER_* (the keys) or SUPABASE_*, and none of the variables a Claude Code session PacedMind runs inside would pass on (`HOST_SESSION_VARS`: with them, the agent's Claude Code saves no transcript), which the terminal scripts also clear. URLs handed to agents use the port the server actually listens on (`process.env.PORT`).
- Dependencies (`edges`, `Dependency` in `src/lib/types.ts`) only order the work: nothing starts a session by itself, every session is started by you or by an agent's request you allow. A task handed back `partial` or `blocked` doesn't count as finished (`repo.heldOutcomes()`), so what waits for it waits until the user marks it done; `dependencies.ts` and `timeline.ts` share this rule. There are no flows any more: their columns (`edges.mode` and `at_time`, `tasks.flow_x` and `flow_y`, `sessions.continues_session_id`, `devices.flows_on`, and locally `projects.flow_on`) stay, unused, so older apps keep working; nothing new reads or writes them.
- Where a session runs is its surface: `terminal` or `desktop` (the Claude or Codex app, opened with `claude://code/new` or `codex://new`, first message written but not sent) on a computer, or `cloud` (`claude --cloud` in a terminal, `codex cloud exec` in the background with the project's `codexEnv`, which is held to a pattern because it reaches a command line). A task's `runIn` null means the terminal when the CLI is there, else the app (`surfaceOf()`). Cloud sessions can't reach the MCP server: the user marks them finished, and Codex cloud tasks are checked by `cloud.ts` on the computer that sent them. A task can name its computer (`deviceId`, else its project's): its sessions start only there, and "Start" elsewhere asks that computer with a launch request. A task's own `folder` is this computer's setting, like a project's.
- A task's `needs` (what its agent needs from the computer its session runs on) only steer where it goes: `offeredDevice` and the Run on a computer sheet prefer a computer whose agent has them (online first); Start here, when the agent here lacks one and another computer has them all, answers `remote` with `missingHere`, and the sheet offers Start here anyway (`startSessionAction(…, anyway)`); an agent's request to start one shows what's missing here (the approval's `missing`). What this computer has is `toolsHere()` in `devices.ts` (its servers everywhere and in the task's folder, its account's connectors and plugins); the others', their `devices.agents` extras. The agent's cloud isn't checked. A request from elsewhere isn't either: its sender picked the computer.
- Dependencies are drawn on the Timeline (`linkTasksAction`) or made by agents (`connect_tasks`): within one project, never a loop. Your own (`human`) tasks can have them too.
- A task's `agent` (who does it, the `Doer` type) is `claude`, `codex`, `human` or null. `human` tasks are the user's: never an agent session, and the auto-planner puts them in the user's time. Null means the project's default agent, else Claude Code; resolve it with `agentOf()` from `src/lib/types.ts`, never `task.agent ?? …`.
- A task in an area but no project is one of the area's To-dos (`/area/[id]/todos`, the first row under each area in the sidebar, counted by `Usage.areas[].loose`). Its `relatedProjectId` says it's about a project without being part of it: that project's page lists it under Related, and it counts nowhere in the project (progress, roadmap). A task's `repeat` (`day`, `weekday`, `week`, `month`) makes it come back once done: `repeatTask` in `ops.ts`, which `afterTaskDone` calls (so every way of marking done does it), creates the next one at its next date (`src/lib/repeat.ts`) and moves the repeat onto it.
